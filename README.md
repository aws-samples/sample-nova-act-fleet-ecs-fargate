# Nova Act Fleet

A reference implementation for running Amazon Nova Act browser-automation fleets on **Amazon ECS Fargate** — with the security, observability, and human-in-the-loop controls Amazon Bedrock AgentCore Browser would otherwise provide.

> **Disclaimer**
>
> This is sample code provided for demonstration and educational purposes. It is not intended for production use without additional review, testing, and hardening — see [`SECURITY.md`](SECURITY.md) for known trade-offs.

## What this is

This project shows how to operate a fleet of Amazon Nova Act browser-automation agents on AWS using your **own VPC, your own IAM, and your own observability stack** — without depending on Amazon Bedrock AgentCore Browser. It uses the Nova Act SDK directly and adds the production controls AgentCore Browser would otherwise provide: defense-in-depth security, human-in-the-loop (HITL) escalation, structured logging to CloudWatch, screenshot artifacts in S3, batch orchestration, retry policy, and CloudFormation-based deployment.

It is intended for teams that need production browser automation but **cannot or will not use AgentCore Browser** today:

- Regulated workloads with custom network or data-residency requirements that AgentCore's managed runtime doesn't satisfy.
- AWS accounts without Bedrock access in their region, or those waiting for AgentCore to reach more regions.
- Organizations standardized on ECS, CloudFormation, and CloudWatch that don't want to introduce a separate managed agent runtime into the stack.

If AgentCore Browser fits your environment, **use it instead** — see the official [Nova Act + AgentCore Browser quickstart](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-quickstart-nova-act.html) and the [`aws-samples/sample-browser-order-automation-agentcore`](https://github.com/aws-samples/sample-browser-order-automation-agentcore) sample. This project only makes sense when AgentCore Browser is off the table. See [`docs/why_not_agentcore.md`](docs/why_not_agentcore.md) for when that is.

## Why this exists (what it differentiates from)

Every published Nova Act sample today assumes AgentCore Browser. This project fills the gap for teams that need to run a **production Nova Act fleet on Amazon ECS Fargate**, in their own VPC, with the security, observability, and HITL plumbing they have to build themselves when AgentCore is unavailable.

| Existing AWS resource | What it covers | What it does not cover |
|---|---|---|
| [`aws/nova-act`](https://github.com/aws/nova-act) | SDK reference, single-agent examples | No fleet orchestration, no security model, no production deployment |
| [`amazon-agi-labs/nova-act-samples`](https://github.com/amazon-agi-labs/nova-act-samples) | CDK examples for AWS deployments | CDK only, no CloudFormation, no end-to-end production controls |
| [`aws-samples/sample-browser-order-automation-agentcore`](https://github.com/aws-samples/sample-browser-order-automation-agentcore) | Multi-retailer order automation with HITL | Assumes AgentCore Browser; no path for accounts that can't use AgentCore |
| [`aws-samples/sample-agents-with-nova-act-and-mcp`](https://github.com/aws-samples/sample-agents-with-nova-act-and-mcp) | Nova Act + MCP integration | Different surface area; no fleet or production-deployment guidance |
| [Nova Act + AgentCore Browser docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-quickstart-nova-act.html) | Quickstart for AgentCore-managed Nova Act agents | Only the AgentCore deployment path |

The intersection — *non-AgentCore + production deployment + CloudFormation + Amazon ECS Fargate + replicate AgentCore's session isolation, observability, and identity primitives yourself* — is the space this project fills.

Compared to AgentCore Browser specifically, this project shows how to replicate (or accept the loss of) each managed feature:

| AgentCore Browser feature | Equivalent in this project |
|---|---|
| Managed Chromium session lifecycle | Container-managed via Playwright in ECS Fargate |
| Session isolation | VPC private subnet + per-task ephemeral container/session |
| Live viewing and session replay | Per-step screenshots in S3 + Nova Act SDK's local HTML session log |
| CloudTrail logging of agent actions | Structured CloudWatch Logs from `ObservabilityManager` + CloudTrail on AWS API calls |
| Domain restrictions | `SecurityManager.validate_domain` (allowlist + blocklist, blocklist precedence) |
| Identity isolation (AgentCore Identity) | Least-privilege IAM per deployment pattern, generated by `SecurityManager.get_iam_policy` |
| Built-in scaling | `ThreadPoolExecutor` in `FleetOrchestrator` (process-local) or autoscaled ECS service |
| Built-in HITL | `HITLManager` → SNS topic + optional DynamoDB state |

### Core components

| Component | Responsibility |
|---|---|
| `WorkflowAgent` | Single execution unit. Wraps `NovaAct` as a context manager, validates domains *before* the session opens, enforces a 30-minute session timeout, captures screenshots, emits structured logs. Exposes `execute_task`, `extract_data`, `automate_form`, `run_checkout_flow`, and `run_qa_test`. |
| `FleetOrchestrator` | Validates 5 MB payload limit, dispatches tasks via `ThreadPoolExecutor`, aggregates results into a `BatchResult`, escalates retry-exhausted failures to HITL, and publishes CloudWatch metrics. |
| `SecurityManager` | Implements security layers 1–4: regex prompt filtering, domain allow/block, tool registration, file-access gate. Generates least-privilege IAM policies per deployment pattern. |
| `ObservabilityManager` | Structured JSON logs to CloudWatch Logs, custom metrics under the `NovaActFleet` namespace, S3 artifact storage, and a `LowSuccessRate` alarm. |
| `HITLManager` | Publishes failed-task payloads to SNS, optionally records state in DynamoDB, captures `HITLResolution` events, and tracks the running escalation rate against a configurable target (default 5%). |

### Deployment target

This project targets **Amazon ECS Fargate**: the CloudFormation template at `templates/ecs_deployment.yaml` deploys a VPC, NAT Gateway, ECS cluster, ECR repository, IAM roles, and a CloudWatch log group, all wired for the Nova Act workflow agent container. AWS Lambda was evaluated as an alternative compute target; it is documented in [`docs/decision_matrix.md`](docs/decision_matrix.md) for completeness but is not shipped in v0.2 — see "Why no Lambda template?" in that file for the rationale.

If AgentCore Browser fits your environment, use it instead — see [`docs/why_not_agentcore.md`](docs/why_not_agentcore.md).

## Quick start (local)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -e ".[dev]"
python -m playwright install chromium

cp .env.example .env
# Edit .env and set NOVA_ACT_API_KEY=<your-key>
# Get one at https://nova.amazon.com/act?tab=dev_tools

python examples/run_single_agent.py
```

A successful run prints `Status: success`, the agent's natural-language output, and a duration of roughly 30–90 seconds. The Nova Act SDK also writes a local HTML session log with every think/click/return step — the path is in the run output.

## Programmatic usage

```python
from nova_act_fleet.agent import (
    AgentConfig,
    DeploymentPattern,
    FleetConfig,
    FleetOrchestrator,
    TaskDefinition,
)

agent_config = AgentConfig(
    starting_url="https://your-app.example.com",
    api_key="<from your secret store>",
    allowed_domains=["your-app.example.com"],
    headless=True,
)

fleet_config = FleetConfig(
    concurrency_limit=5,
    agent_config=agent_config,
    deployment_pattern=DeploymentPattern.ECS,
    hitl_enabled=True,
)

orchestrator = FleetOrchestrator(config=fleet_config)

tasks = [
    TaskDefinition(
        task_id=f"task-{i}",
        task_type="custom",
        starting_url="https://your-app.example.com",
        prompt="Open the dashboard and capture the headline metric.",
    )
    for i in range(5)
]

result = orchestrator.submit_batch(tasks)
print(f"Success rate: {result.success_rate:.1%}")
```

## Deploying to AWS

Detailed steps are in [`docs/deployment_guide.md`](docs/deployment_guide.md). Short version (the two `<...>` parameters are required — see the guide for how to create the bucket and the secret):

```bash
aws cloudformation deploy \
  --template-file templates/ecs_deployment.yaml \
  --stack-name nova-act-fleet-ecs \
  --parameter-overrides \
    EnvironmentName=nova-act-fleet \
    S3ArtifactBucketName=<your-artifact-bucket-name> \
    NovaActApiKeySecretArn=<your-secret-arn> \
    ContainerImageTag=v1 \
    DesiredTaskCount=0 \
  --capabilities CAPABILITY_NAMED_IAM \
  --region us-east-1
```

> **Region note:** Amazon Nova Act is currently in `us-east-1` only. Deploy all resources there.
>
> **Container image note:** the ECS template provisions an ECR repository and IAM. You build and push the agent container image yourself; the `docs/deployment_guide.md` walks through it. We deliberately do not publish a public image so that the supply chain stays inside your account.

## Configuration reference

All configuration is constructor-driven on Pydantic models. Constraints are enforced at validation time.

### `AgentConfig`

| Field | Default | Notes |
|---|---|---|
| `starting_url` | required | Initial page for the session |
| `api_key` | `None` | Forwarded to `NovaAct(nova_act_api_key=...)`; falls back to the `NOVA_ACT_API_KEY` env var if `None` |
| `allowed_domains` | required | Min length 1; enforced by `SecurityManager` before session opens |
| `blocked_domains` | `[]` | Takes precedence over allowlist |
| `headless` | `True` | Run Chromium headless |
| `session_timeout_seconds` | `1800` | Max 1800 (30 min); enforced via `threading.Timer` |
| `max_steps` | `100` | Max 100 |
| `max_prompt_length` | `10000` | Max 10000 characters |

### `FleetConfig`

| Field | Default | Notes |
|---|---|---|
| `concurrency_limit` | `10` | Workers in `ThreadPoolExecutor` |
| `max_payload_size_bytes` | `5_242_880` | 5 MB; oversized tasks are rejected |
| `agent_config` | required | Nested `AgentConfig` |
| `deployment_pattern` | required | `ECS` (the supported target in v0.2). The enum exposes `LAMBDA` and `AGENTCORE` for forward compatibility but neither is wired up in v0.2. |
| `hitl_enabled` | `True` | Toggle HITL escalation |

### `ObservabilityConfig`

| Field | Default |
|---|---|
| `cloudwatch_log_group` | required |
| `s3_bucket` | required |
| `s3_prefix` | `nova-act-artifacts` |
| `artifact_retention_days` | `90` |
| `metric_namespace` | `NovaActFleet` |
| `alarm_success_rate_threshold` | `0.90` |
| `alarm_evaluation_period_minutes` | `15` |

### `HITLConfig`

| Field | Default |
|---|---|
| `sns_topic_arn` | required |
| `dynamodb_table_name` | `None` |
| `escalation_rate_target` | `0.05` |

## Task lifecycle

`TaskStatus` values: `pending`, `running`, `success`, `failed`, `escalated`, `timeout`, `rejected`.

```
TaskDefinition
    │
    ▼
FleetOrchestrator.submit_batch
    │  validates 5 MB payload   ──► REJECTED
    │
    ▼
WorkflowAgent.execute_task
    │  prompt length check      ──► REJECTED
    │  domain validation        ──► raises AgentSessionError
    │  NovaAct session opens
    │  30-min timer started
    │
    ├── act() returns           ──► SUCCESS
    ├── timer fires              ──► TIMEOUT
    └── exception                ──► FAILED
                                       │
                                       ▼
                          retry up to max_retries
                                       │
                                       ▼
                          FleetOrchestrator.escalate_to_hitl
                                       │
                                       ▼
                                  ESCALATED
```

## Project status and limitations

- Nova Act is launch-region-locked to `us-east-1`. All AWS resources must live there.
- AgentCore Browser is **out of scope by design**. The `DeploymentPattern.AGENTCORE` enum value is preserved for compatibility but no template, example, or doc targets it. If you can use AgentCore, you should — see the linked official quickstart.
- `SecurityManager.validate_domain` does an exact hostname match; subdomain wildcards (e.g. `*.example.com`) are not yet supported.
- Default ARNs in `FleetOrchestrator._hitl_manager` are placeholders. Inject your own `HITLManager` via `set_hitl_manager(...)` for production.
- HIPAA and PCI-DSS are not in scope at Nova Act launch; do not process PHI or cardholder data through this project.

## Known gaps and operational notes

These were uncovered during the v0.2 end-to-end deployment. They are real and worth tracking; some are framework bugs, some are AWS service constraints, some are environment quirks.

### Framework gaps

- **`execute_task` does not retry on its own.** `TaskDefinition.max_retries` is plumbed through the model and read by `FleetOrchestrator._escalate_to_hitl` to decide whether a failure has exhausted retries, but `WorkflowAgent.execute_task` runs the prompt exactly once. The retry loop only exists today in `WorkflowAgent.automate_form`. The HITL escalation path still works — when `task.max_retries=0`, a single failure satisfies `result.retry_count (0) >= task.max_retries (0)` and the task escalates as expected — but `max_retries=3` on a non-form task does not actually produce three attempts. Verified end-to-end in the smoke deploy. Fix candidate for a follow-up release: factor a shared retry decorator out of `automate_form` and apply it to `execute_task`.
- **Screenshot capture is racy.** When the post-act screenshot grab races a fast `nova.act()` return, the saved PNG can be empty (0 bytes). The screenshot is best-effort by design (logging failures must not break the task), but two of five PNGs in our smoke runs were empty. Worth tightening to capture inside the `with NovaAct(...)` block before the page closes.

### AWS Fargate constraints

- **`LinuxParameters.SharedMemorySize` is not supported on Fargate.** Earlier drafts of `templates/ecs_deployment.yaml` set it to 2048 MB; CloudFormation rejects this with `Fargate compatible task definitions do not support sharedMemorySize`. The shipped template omits it. Chromium runs against Fargate's default 64 MB `/dev/shm`; for single-page Nova Act sessions this is enough. If a workload needs more, override Chromium's `/dev/shm` use by passing a custom Playwright instance to `NovaAct(playwright_instance=...)` with `--disable-dev-shm-usage`.
- **ECS task `--overrides` is capped at 8 KB.** `aws ecs run-task --overrides` rejects payloads larger than 8192 bytes. This affects how you deliver large `TaskDefinition` payloads to a Fargate task; for production, route large payloads through SQS, S3, or DynamoDB instead of env-var overrides.
- **Retained ECR repositories and CloudWatch log groups block re-deploy.** The template marks the ECR repo and the task log group `DeletionPolicy: Retain` to preserve images and logs across stack updates. After a `ROLLBACK_COMPLETE` failure, those resources survive and the next `aws cloudformation deploy` fails the early-validation hook with a name collision. Fix: delete the repo and log group manually before re-deploying, or import them into the new stack.

### Container image quirks

- **`NOVA_ACT_SKIP_PLAYWRIGHT_INSTALL=1` must be set in the image.** Even when Playwright Chromium is pre-installed at `PLAYWRIGHT_BROWSERS_PATH`, the Nova Act SDK runs an install check at session start and fails with `StartFailed: Failed to install Playwright browser binaries` if it can't reach the Playwright CDN (which the security group blocks by design). Setting `NOVA_ACT_SKIP_PLAYWRIGHT_INSTALL=1` in the Dockerfile makes Nova Act trust the pre-installed binaries. The shipped Dockerfile does this.
- **Cross-architecture builds on Apple Silicon are slow.** The Dockerfile targets `linux/amd64` because Fargate's default is amd64. On Apple Silicon hosts running Podman or Docker Desktop, this means cross-arch QEMU emulation. The first clean build takes 7–10 minutes; subsequent rebuilds with cached Chromium and FFmpeg layers are seconds.
